## 同机 CPU 延迟与内存

下列各行来自**同一个独占集群资源分配中的一次测量**：Intel Xeon Platinum 8558、Linux x86-64、分配 16 核、每个服务 4 个 CPU 线程，未使用 GPU。原版与 ONNX 为 FP32，GGUF 为 Q8_0 backbone + F32 视觉文件，其内存/延迟权衡包含精度差异。原模型 revision 为 `ae8bdf7606c0dbd627301174c9cb800240fb4ec7`。

每个后端/模态使用新服务进程，先执行一次冷请求，再预热 2 次，最后顺序重复 7 次，且每次测量的答案都必须与冷请求完全相同。p50/p95 在有序样本上采用线性插值。并发数为 **1**，测的是延迟，不是吞吐。启动时间包括解释器/运行时 import、模型初始化和健康就绪；ONNX 在首请求中才初始化图会话，因此冷请求慢于热请求。**未清空操作系统页缓存**，“冷”指新进程，不是冷磁盘。

<PerformanceTable />

峰值内存是独立服务进程 Linux `VmHWM` 的 RSS 高水位，包括驻留的 mmap 页、库及加载的模型流水线；不等于模型文件大小、资源分配上限、GPU 显存或最低内存需求。

各路径使用**相同输入字节、问题、候选顺序、temperature=1.0 与媒体预算**。成功路径的输入 token 一致：文本 166、图片 215、视频 839。图片预算为 65,536–1,638,400 像素；直接视频均匀采样 16 帧，总像素预算为 131,072–2,097,152。精确输入/媒体哈希及每次采样保存在 JSON。媒体字节在计时前准备，不包含远端客户端上传或网络素材下载。

Transformers 5.20 用 torchcodec 解码视频文件；原版环境使用 torchcodec 0.17.0（CPU）及 PyAV 17.1.0 自带的 FFmpeg 8 库。原版与 ONNX 的重复请求答案全部一致：原版每种输入 8 次，生产 ONNX 服务每种输入 4 次。

原版/ONNX 性能测试采用包裹真实 `predict` 的轻量本机 HTTP 测量适配器，不是 SGLang/vLLM，也不是生产 SDK HTTP 栈。生产 ONNX SDK 服务另行做了检查。

## 协议与媒体能力

<BackendCapabilities />

表中列出的两种协议均继续保留。Decisions 使用 `input`、有序问题列表、`predicate`、字符串/布尔型 choice 值和带标签的 score 等级。SystemOne 使用 `state`、按 ID 的问题字典、`noul`、字符串键 `criteria` 和有序评分标准。score 是从零开始的等级索引的概率加权平均。数字型 choice 值会被拒绝；JavaScript 对象中的数字外观**字符串**键遵循 JS 对象顺序规则。候选顺序重要时使用 Decisions 数组；JS HTTP 客户端拒绝 `Map`，不会静默改序。

有限正数的**标量** temperature 是跨后端的公共范围。原版/ONNX 旧协议的按题型温度字典不代表 GGUF 或 Decisions 也可移植支持。一个请求内候选顺序保持一致；主动改变顺序会改变模型提示和概率，不承诺排列不变性。

原版/ONNX 本地调用可读取本地素材。HTTP 按能力使用内联图片/视频 data URL；生产 ONNX 服务禁止客户端本地路径。托管 API 和 GPU 插件采用单张图片，视频标注应用会明确先抽帧。`Valen.local` 是 **ONNX** 加载器，GGUF HTTP 服务使用 `Valen.remote`。这些 SDK 不会使未修改的官方 llama.cpp/Ollama 自动兼容 Valen。

GGUF 测试使用已发布的[运行时 0.2.0 压缩包](https://github.com/Valen-Team/Valen/releases/tag/gguf-runtime-v0.2.0)（SHA256 `4b3b6035adbb99f3bb47c75e55804e1f650f96b35b825d95a6cd4ae85ce39537`，与发布资产一致），以及 `Valen-Team/Valen-Decision-1.5-0.8B-GGUF` 中发布的 Q8_0 与视觉文件。该运行时支持文本、图片和 `bbox` 问题。其直接视频探测返回 HTTP 500（“Failed to load image or audio file”），失败原样保留。请抽帧后按图片发送。

## 固定回归与发布检查

主仓库的 `tests/fixtures/backend-contract.json` 是共享协议夹具，覆盖 choice、predicate/noul、score、混合布尔/字符串候选、候选逆序、1.0/0.5 温度及异常输入。真实检查对比各后端双协议的答案、usage、候选类型/顺序和错误，覆盖原版 FP32、ONNX FP32 测量服务、生产 ONNX SDK 服务和 GGUF 运行时（文本与图片）。已发布的 Python SDK 0.5.0 与 JavaScript SDK 0.4.0 分别连接生产 ONNX 服务和 GGUF 运行时。

快速构造响应检查接入主仓库 CI。官网 CI 检查源文件/输出哈希、双语构建和链接。代码或样例变更后，真实执行哈希失效，须补跑。相关模型/运行时/SDK 发布前，必须在集群缓存上执行真实检查，并校验固定的发布证据；CI 不下载权重。详见[发布与复现流程](https://github.com/Valen-Team/Valen/blob/main/scripts/validation/README.md)。

SDK 检查脚本只在服务返回 HTTP 4xx 时才把异常用例记为通过。两个 SDK 现在会在发送前拒绝 `duplicate-names` 和 `numeric-choice`，因此报告把这两项列为未通过；在契约夹具中，服务对这两项都返回 HTTP 400。此前在共享登录节点上的三次性能测试尝试均保留：第一次原版视频因缺少 torchcodec 失败，第二次 FFmpeg 库路径不完整，第三次在登录节点过载重启时中断。本页发布的数据只来自上面的独占资源分配中的那一次运行。
