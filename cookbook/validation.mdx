# Measured scope, not a generic speed promise

Validated on **10 November 2026** with **Valen-Decision-1.5**. This page reads the version manifest, performance rows, comparisons and capability matrix directly from their machine-readable sources. The benchmark uses real Valen-Decision-1.5-0.8B weights with a small fixed text case and synthetic diagnostic image/video inputs. These are not representative task-accuracy or production-load benchmarks.

## Same-host CPU measurements

All rows below came from **one benchmark run in one dedicated cluster allocation**: Intel Xeon Platinum 8558, Linux x86-64, 16 allocated cores with four CPU threads per server, no GPU in use. Native and ONNX use FP32; GGUF uses Q8_0 backbone weights with an F32 vision file, so its memory/latency tradeoff includes a precision difference. The source model revision is `ae8bdf7606c0dbd627301174c9cb800240fb4ec7`.

Each backend/modality gets a fresh server process, one cold request, two additional warmups and seven measured sequential requests, and every measured answer must equal the cold answer. p50/p95 use linear interpolation on sorted samples. Concurrency is **one**; this is latency, not throughput. Startup includes interpreter/runtime imports, model initialization and health readiness; ONNX initializes its graph sessions during the first request, so its cold requests are slower than its warm ones. OS page caches were **not cleared**: “cold” means process-cold, not disk-cold.

<PerformanceTable />

Peak memory is the isolated server process's Linux `VmHWM` resident-memory high-water mark, including resident mapped pages, libraries and the loaded model pipeline. It is not the model file size, the allocation limit, GPU memory, or a minimum RAM specification.

The backends receive the **same bytes, questions, candidate order, temperature 1.0 and media budgets**. Successful token counts match: text 166, image 215, video 839. Image budgets are 65,536–1,638,400 pixels; direct video uses 16 uniform frames with a 131,072–2,097,152 total-pixel budget. Exact input/media hashes and raw samples are in the JSON. Media bytes are prepared before the request timer; upload from a remote client or network asset fetch is not included.

Transformers 5.20 decodes video files with torchcodec; the native environment used torchcodec 0.17.0 (CPU) with the FFmpeg 8 libraries bundled with PyAV 17.1.0. Every repeated native and ONNX request returned identical answers: eight requests per input on native, four on the production ONNX service.

The native/ONNX latency server is a small localhost measurement adapter around real `predict`, not SGLang/vLLM or the production SDK HTTP stack. Separate checks exercised the production ONNX SDK service.

## Interface and media capabilities

<BackendCapabilities />

Both protocols remain supported where listed. Decisions uses `input`, an ordered question list, `predicate`, typed string/boolean choice values and labeled score levels. SystemOne uses `state`, an ID-keyed question mapping, `noul`, a string-keyed `criteria` mapping and ordered score criteria. Scores are probability-weighted zero-based level indices. Numeric choice values are rejected; numeric-looking **string** keys in JavaScript objects follow JavaScript object-order rules. Use Decisions arrays when candidate order is significant; the JS HTTP client rejects `Map` rather than silently changing it.

A finite positive **scalar** temperature is the portable intersection. Native/ONNX legacy per-type temperature mappings are not a GGUF or Decisions portability guarantee. Candidate order is preserved within a request; changing the order can change the model's prompt and probabilities. No permutation-invariance promise is made.

Local native/ONNX calls can read local files. HTTP media uses inline image/video data URLs where supported; the production ONNX service disables client-local paths. The hosted API and GPU plugins use a single image, so extract a frame explicitly for the video-tagging application. `Valen.local` is an **ONNX** loader; use `Valen.remote` for GGUF HTTP services. Generic upstream llama.cpp/Ollama does not become compatible through these SDKs.

The GGUF runs used the published [runtime 0.2.0 archive](https://github.com/Valen-Team/Valen/releases/tag/gguf-runtime-v0.2.0) (SHA256 `4b3b6035adbb99f3bb47c75e55804e1f650f96b35b825d95a6cd4ae85ce39537`, matching the release asset) with the Q8_0 and vision files published in `Valen-Team/Valen-Decision-1.5-0.8B-GGUF`. The runtime serves text, images and `bbox` questions. Its direct video probe returned HTTP 500 (“Failed to load image or audio file”); this failure remains published. Use sampled frames sent as images.

## Fixed regression and release checks

One fixture in the main repository, `tests/fixtures/backend-contract.json`, covers choice, predicate/noul, score, mixed boolean/string candidates, reversed candidate order, temperatures 1.0/0.5 and invalid requests. Real checks compare each backend's Decisions and SystemOne answers, usage, candidate types/order and errors. They ran on native FP32, the ONNX FP32 measurement server, the production ONNX SDK service and the GGUF runtime (text and image). The published Python SDK 0.5.0 and JavaScript SDK 0.4.0 were exercised against the production ONNX service and the GGUF runtime.

<NumericalTable />

The numerical gates are choice agreement ≥ 98%, probability MAE ≤ 0.02, maximum probability error ≤ 0.08 and normalized score MAE/maximum ≤ 0.05/0.15. This small protocol fixture checks consistency with the native model, not accuracy against ground truth. All compared input token counts match.

### Cookbook recipes across model sizes

Thirteen Cookbook recipes (text, image and video-frame requests) were run on CPU with the native model and with each ONNX bundle. FP32 bundles made the same decisions as the native model at every size. The `q8-mlp` variant agreed on every decision for 2B, 4B and 9B and on 98.4% for 0.8B, where four of 249 recipe decisions changed; they are listed in the JSON.

Fast synthetic mapping checks run in the main repository CI. Website CI tests source/output hashes, builds both languages and checks links. Code/sample changes invalidate the stored real-execution hashes until rerun. Before a relevant model/runtime/SDK release, run the real checks on cluster caches and validate the pinned release evidence; CI does not download model weights. See the [release and reproduction procedure](https://github.com/Valen-Team/Valen/blob/main/scripts/validation/README.md).

The SDK check scripts count an invalid case as passed only when the service answers with HTTP 4xx. Both SDKs now reject `duplicate-names` and `numeric-choice` before sending, so their reports list those two cases as not passed; the services return HTTP 400 for both in the contract fixture. Three earlier benchmark attempts on a shared login node are preserved: native video failed until torchcodec was installed, the FFmpeg library path was incomplete in the second, and the third was interrupted when the overloaded node was rebooted. The published rows come from the single dedicated run above.
